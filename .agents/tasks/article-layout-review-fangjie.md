# 芳姐文章页布局体验审查

## 摘要结论

本次审查的对象是[线上文章页](https://liuning0820.github.io/2026/08/28/%E8%8A%B3%E5%A7%90%E7%9A%84%E5%85%89%E8%8D%A3%E9%80%80%E4%BC%91%E6%AC%A2%E9%80%81%E4%BC%9A.html)，并结合仓库中的 Jekyll 模板、CSS 和文章源文件进行比对。页面当前最大的体验问题不是正文宽度或字体，而是文章身份信息和阅读后的去向不够明确：读者看完标题后看不到日期、作者和标签，读完正文后只能看到英文的前后文章链接，随后马上进入体量较大的公众号二维码区。

推荐优先级如下：

- **P0：补齐文章头部元信息。** 在标题下显示发布日期、作者和标签，并使用中文或中英一致的文案。文章源文件已经有 `author` 和 `tags`，Jekyll 也能从文件名推导文章日期，因此这是低风险、高收益的模板改动。
- **P1：重做文章结束区和发现路径。** 在前后文章导航旁增加“返回文章列表”，把前后链接改成更容易扫描的卡片或两列区域，并增加同标签或相关文章入口。当前页没有明显的博客内容发现路径。
- **P1：收敛站点级导航和订阅区。** 将博客核心入口与 FeedReader、Presentations、Channels、Apps 等外部项目分组；把“Subscribe to get updates”改成与实际公众号二维码相符的中文说明，或另加真正的 RSS/邮件订阅说明。
- **P1：做一次真实浏览器的移动端和键盘验收。** 当前源码已经补上移动菜单的 `aria-expanded`、`aria-controls`、Escape 关闭和焦点返回，但 CSS 仍有下拉子菜单只靠 `:hover`、菜单高度固定为 `500px` 等风险，不能只靠静态源码判断交互完成度。
- **P2：为有图片的文章补充可见图注，并统一图片语义。** 本文没有正文图片，所以这不是本文当前问题；仓库中的旅行文章使用 Markdown alt 文本，但模板没有 `figure/figcaption` 结构，图片说明不会自然成为可见图注。
- **P2：完善分享和搜索摘要。** 线上页已有基本 Open Graph 和 Twitter Card，但没有 `og:image`、发布时间等文章级信息；当前 description 实际以文章标题和正文开头拼接而成，适合搜索的摘要仍可进一步控制。

## 审查范围和证据边界

本次审查通过线上页面响应内容和本地源码完成，没有修改生产代码、没有提交 commit，也没有启动本地服务。线上检查确认了 HTML 结构、文本、链接和 head 元数据，但没有真实浏览器的像素截图、滚动体验、触摸操作或屏幕阅读器结果。因此，下面明确区分已经观察到的事实、基于源码的判断，以及必须用真实浏览器验证的事项。

审查开始时工作区已经存在未提交变更：`_posts/2026-06-26-慈溪市上林湖越窑青瓷博物馆.md` 被修改，`.agents/tasks/personal-blog-review.md` 未跟踪。本报告文件是按任务要求新增的审查产物；没有改动上述生产文件。

## 已观察到的事实

### 文章结构和正文阅读

线上页面的主内容是一个 `h1` 和九个普通段落，没有文章副标题、`h2` 小节、目录、引言摘要块或正文图片。线上 HTML 中的唯一站点级 `h3` 是订阅区的 “Subscribe to get updates”。这与目标文章源文件的结构一致：第 8 行是唯一的 `#` 标题，第 11--27 行是连续叙事段落，没有图片或小标题（`_posts/2026-08-28-芳姐的光荣退休欢送会.md:8-27`）。

正文的叙事顺序是清楚的：偶遇退休消息、回忆唯一一次处理 WiFi、参加欢送会、听到职业压力，最后回到作者自己的退休想象。对于这篇长度适中的个人叙事，没有目录并不是问题。当前页面更像一篇干净的短文，而不是需要复杂导航的长文。

本地 CSS 给正文区域设置了 `720px` 最大宽度，外层容器最大宽度为 `1000px`，正文使用 `18px` 字号和 `1.7` 行高（`css/main.css:22-30,150-164`）。这是一个可读性基础较好的默认值，中文字符不会因为内容区过窄而形成过多短行。标题使用 Merriweather、正文使用 Inter（`css/main.css:22-25,170-176`；字体加载位于 `_layouts/default.html:26-32`）。

但模板没有文章专用的正文样式。`post` 布局只输出 `{{ content }}`，再直接输出前后文章导航（`_layouts/post.html:1-15`）；段落间距主要依赖浏览器默认样式。**判断：**本文目前不会因为 CSS 而出现明显的“挤成一团”问题，但段落节奏没有被站点明确设计。以后遇到更长的中文文章、引用、代码或小标题时，页面可能会表现出不同的间距和层次。

### 标题、日期和元信息

线上页能看到文章标题，但在标题下没有日期、作者、标签、阅读时长或分类。目标文章的 front matter 已有 `author: liuning0820`、`tags: [life]` 和 `comments: true`（`_posts/2026-08-28-芳姐的光荣退休欢送会.md:1-6`），而 `post` 布局没有读取这些字段（`_layouts/post.html:5-15`）。文章文件名包含 `2026-08-28`，归档页也会输出 `post.date`（`all.html:8-12`），但文章详情页没有展示它。

这是本文最突出、也最容易快速修复的布局问题。个人博客文章需要让读者在进入正文前快速回答“什么时候写的、谁写的、属于什么主题”。当前标题之后直接进入第一段，视觉上缺少一个信息层级，也削弱了文章在分享链接或再次访问时的辨识度。

线上 head 已有 `title`、`description`、canonical、`og:type/title/description/url` 和 Twitter 的 title、description、url（`_layouts/default.html:10-24`）。但线上实际抓到的 description 是文章标题紧接正文开头的长字符串，并在约 160 个字符处截断。**事实：**基础分享元标签存在。**判断：**description 应该改为文章明确的摘要或第一段的干净版本，避免标题重复；这属于内容发现和分享体验问题，不是正文排版问题。

### 文章结束、导航和内容发现

线上页的文章末尾有上一页和下一页链接。模板使用 `page.previous` 和 `page.next`，文案固定为英文 “Previous Post” 和 “Next Post”，链接后再接文章标题（`_layouts/post.html:7-14`）。目标页在源码层面连接到相邻的《浙江徒步之雪窦岭》和《球场上的镜像神经元》文章。**事实：**页面有连续阅读入口。**问题：**入口没有“返回全部文章”，也没有根据 `life` 标签继续浏览的入口；对中文读者而言，固定英文文案也增加了识别成本。

`all.html` 提供全部文章列表和标签云，但详情页没有显眼地把读者引回该页（`all.html:6-34`）。站点导航把 `/all.html` 命名为 “Blogs”，同时还放入 FeedReader、Presentations、Channels、Apps、About、RSS 和搜索（`_layouts/default.html:46-83`）。这些功能本身有价值，但在文章阅读场景中，核心路径“返回博客、浏览主题、读下一篇”与外部项目入口没有分组，内容发现的优先级不够清楚。

### 页首页尾和视觉层次

文章页顶部先显示品牌图片，再显示横向主导航；正文位于全局容器内（`_layouts/default.html:37-98`）。导航和正文之间有明显的页面级边界，正文本身保持了白底、蓝色标题和深灰文字的简单视觉语言。

正文结束后，模板固定插入订阅区，再插入页脚（`_layouts/default.html:100-137`）。订阅区有 `2rem` 内边距、`3rem` 上下外边距、浅灰背景和 `180px` 二维码（`css/main.css:324-361`）。线上文章实际显示的二维码是公众号二维码，旁边的文案是“关注公众号：对刘谈心”，但区块标题仍是英文 “Subscribe to get updates”。**判断：**在一篇短文结束处，这个区块的视觉重量可能超过文章末尾和前后文导航，读者容易把它理解为打赏或营销区，而不是博客订阅；文案和实际动作也不完全匹配。

页脚目前只有 Email、GitHub、B站，以及 “edit this page” 和 “report an issue”（`_layouts/default.html:116-137`）。它能服务维护和联系，但没有重复博客首页、文章列表、标签或 RSS 的阅读入口。建议把维护入口降为次要信息，把阅读导航作为页脚的第一组链接。

### 图片和图注

目标文章正文没有图片，因此线上页没有正文图片溢出或图注缺失的实际问题。站点对普通 Markdown 图片只有 `p > img { max-width: 100%; height: auto; }` 规则（`css/main.css:363-366`）。相邻的旅行文章使用 `![描述]` 写入 alt 文本，例如《五磊山：从藏云溪走到五磊讲寺》连续使用图片 alt（`_posts/2026-06-27-浙江徒步之五磊山.md:15-48`）。

**事实：**alt 文本能为无障碍和图片加载失败提供替代内容。**判断：**alt 文本不会自动变成视觉图注，读者在正常阅读时看不到“这张图是什么”的说明。对旅行、教程和图片较多的文章，模板或 Markdown 约定应支持可见 `figcaption`，并保留有意义的 alt。这个建议适用于站点整体，不需要为本文增加无关图片。

## 推测和需要真实浏览器验证的事项

### 移动导航

当前 HTML 已给菜单按钮初始 `aria-expanded="false"` 和 `aria-controls="mobile-menu"`，脚本实现了点击切换、Escape 关闭、关闭后返回按钮焦点，以及点击外部关闭（`_layouts/default.html:43,140-182`）。这说明此前的移动菜单可访问性修复已经进入源码，不能再把“缺少初始 ARIA 状态”列为当前事实问题。

仍有两个风险需要浏览器验证。第一，Apps 子菜单的默认 CSS 是 `display: none`，桌面端只通过父项 `:hover` 展开；移动端虽然把它改成静态定位，却没有在同一媒体查询中显式改为 `display: block` 或提供独立的展开按钮（`css/main.css:425-454,545-560`）。**推测：**触摸设备上 Apps 子菜单可能无法稳定打开。第二，移动主菜单打开时固定 `max-height: 500px`（`css/main.css:513-524`），当前主导航还包含搜索表单和 Apps 子菜单。**推测：**在较窄屏幕或字体放大时，菜单底部可能被裁切或出现不可见焦点目标。

必须在至少 `320px`、`375px`、`390px` 和 `768px` 宽度检查：菜单是否完全展开、Apps 子项是否可触摸、搜索框是否横向溢出、打开/关闭按钮是否保持可见、Escape 后焦点是否回到按钮。还要用键盘从按钮依次移动焦点，确认没有焦点落入 `visibility: hidden` 的内容。

### 阅读宽度、长中文段落和横向溢出

本文标题在移动端会从 `2.4rem` 降到 `1.8rem`，标题和首页元信息使用 `overflow-wrap: anywhere`（`css/main.css:170-197,562-568`）；图片也限制为容器宽度以内（`css/main.css:363-366`）。**事实：**源码已经考虑了标题和图片的基本断行。

**推测：**正文没有统一的 `overflow-wrap`，也没有针对 `pre`、代码、表格、长英文 URL 或引用块的规则。本文只有中文普通段落，所以不太可能产生横向溢出；其他中文长文混入链接、英文产品名或代码时仍可能溢出。需要在真实浏览器中用目标页面和一篇包含图片、引用、长 URL 的文章分别检查桌面与移动宽度。

### 字体、焦点和实际视觉层次

源码定义了 18px 正文、1.7 行高、720px 内容宽度和蓝色标题，这套参数从设计上支持长文阅读（`css/main.css:22-25,150-176`）。但本次没有使用真实浏览器截取页面，也没有验证 Google Fonts 加载失败时的回退字体、实际中文字体字宽、标题换行、首屏高度、链接对比度或浏览器缩放后的节奏。以上属于**需要真实浏览器验证**的事项，不应写成线上已经观察到的像素级结论。

建议在浏览器中分别记录：桌面 1440px 和 1024px、断点附近 768px、移动 390px 和 320px；检查标题是否在首屏形成明确焦点，正文是否出现过长行，九个段落是否有足够分隔，前后文章链接是否容易找到，二维码是否抢过正文结尾，以及键盘焦点是否清晰可见。

## 优先级建议

### P0：文章头部增加元信息

修改 `post` 布局，在 `{{ content }}` 实际输出的文章标题下增加统一的文章 meta 行。建议至少包含：`page.date | date_to_string`、`page.author`、第一个标签或分类。日期可以沿用站点现有的英文格式，也可以统一成中文日期；关键是所有文章保持同一格式。对本页来说，这会直接利用现有 front matter 和文件日期，不需要先修改文章正文。

建议新增文章级 class，而不是继续复用首页的 `.gh-post-title`。这样可以分别控制详情页标题、meta、正文段落和首页列表，避免以后为了首页扫描密度而意外改变长文阅读体验。

### P1：建立清晰的读后路径

把当前英文的上一页/下一页改成中文，并为每个链接显示方向和标题，例如“上一篇：浙江徒步之雪窦岭”和“下一篇：球场上的镜像神经元”。同一区块增加“返回全部文章”，必要时增加当前标签链接。文章较短时不需要目录；只有超过一定长度且存在多个 `h2` 时才显示目录，避免给这篇文章增加不必要的界面。

内容发现可以先采用低成本方案：详情页提供返回文章列表、标签入口和一篇相关联文章。后续再根据 Google Analytics 或站内搜索数据决定是否做“相关文章”算法，不要先引入复杂插件。

### P1：重排站点导航和订阅区

将 Home、Blogs、RSS、About 视为博客主导航，将 FeedReader、Presentations、Channels、Apps 视为外部项目或工具入口。桌面端可以保留同一导航栏，但需要视觉分组或下拉层级；移动端优先显示博客主导航。

把订阅区标题改成准确的中文，例如“关注公众号：对刘谈心”，并补一句说明读者会得到什么。如果目标是公众号关注，就不要使用容易让人期待邮件订阅的 “Subscribe to get updates”。可以把区块缩小或放在页脚前的次要位置，让文章结尾和阅读导航先完成。

### P1：移动端和键盘验收后再决定是否改交互

先用真实浏览器验证当前菜单。若 Apps 在触摸设备打不开，使用明确的按钮和 `aria-expanded` 控制子菜单；若 `500px` 高度造成裁切，改为内容自适应并确保打开区域不遮住正文。不要仅凭静态检查再引入新的菜单脚本，因为当前代码已经覆盖了主菜单的基本键盘关闭和焦点返回。

同时给搜索输入框增加可见或屏幕阅读器可用的 label。当前模板只有 `placeholder="Search..."`，没有 `<label>`（`_layouts/default.html:74-81`）。这项改动小，能改善键盘、屏幕阅读器和中文用户使用英文占位提示时的理解成本。

### P2：统一图片和文章内容表现

为图片文章确定一个可复用的 Markdown 约定：图片拥有描述性的 alt，必要时使用 `figure` 和 `figcaption` 显示图注；图注字号和颜色要弱于正文，但不能低到不可读。对本文不建议增加图片或人为插入分节标题，先保持作者原有的短篇叙事节奏。

### P2：控制搜索和社交分享摘要

给重要文章补充明确的 `description` 或 `summary` front matter，让 head 模板优先使用作者提供的摘要。模板可以继续保留当前的 `strip_html`、换行清理和长度截断。若站点希望社交卡片带预览图，再统一提供安全的 `og:image`，不要为没有合适封面的文章生成空图片地址。当前模板的 OG/Twitter 基础字段已存在，不需要重复添加。

## 建议的验证方式

本次没有运行构建、测试或本地服务，以遵守只读调查要求。后续实现时，项目文档建议使用 `bundle exec jekyll serve` 进行本地预览（`README.md:3-22`）；GitHub Pages 工作流使用 `bundle exec jekyll build --future --baseurl "${{ steps.pages.outputs.base_path }}"`（`.github/workflows/jekyll.yml:21-42`）。实现后至少应完成以下检查：

1. 运行 `bundle exec jekyll build --future`，确认目标文章、首页、归档页和 RSS 都能生成。
2. 在桌面和移动视口检查本文的头部 meta、九个段落、前后文章导航、返回列表入口和订阅区顺序。
3. 在 `320px`、`375px`、`390px`、`768px` 和桌面宽度检查导航、搜索、标题、正文、链接和二维码是否出现裁切或横向滚动。
4. 使用键盘完成打开菜单、访问 Apps 子项、Escape 关闭、焦点返回和搜索提交；用屏幕阅读器或自动化无障碍工具确认按钮、导航、输入框和 RSS 图标有可理解名称。
5. 对至少一篇含图片的旅行文章确认图片有描述性 alt、可见图注按约定出现，并且图片不会超出 720px 内容区。

## 结论

本文正文的基础阅读参数已经合理，短篇叙事也不需要目录或复杂卡片化。最先值得做的是文章标题下的日期/作者/标签，以及文章末尾的中文导航和返回文章列表；这两处直接改善“我正在读什么”和“接下来还能读什么”。随后再处理移动菜单的真实设备行为、订阅区文案和全站图片图注。这样可以先获得明显的博客阅读体验提升，再处理需要更多设计和验证的全站重构。
